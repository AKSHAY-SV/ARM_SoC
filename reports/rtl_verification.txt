Hierarchy check
---------------
- soc_top instantiates: reset_sync(u_reset_sync), datapath(cpu),
  instr_mem(imem), data_mem(dmem), apb_subsystem(apb). All instances
  resolve; no undriven/missing modules. (Yosys `hierarchy -check -top
  soc_top` => clean.)
- apb_subsystem instantiates apb_interconnect + gpio/timer/spi/plic +
  apb_uart_wrapper(uart_final -> apb_uart -> uart_regs, uart_top).
- CPU datapath (Data_Path) instantiates pc, control_unit, imm_gen,
  reg_file, alu, mac_unit. alu/mac are single-module (M-extension
  multiply/divide/remainder implemented behaviorally inside alu.v;
  mac_unit implements the accumulator for RISC-V M extension).
- No orphan/unconnected major blocks.

Compile/elaborate/lint
----------------------
- iverilog -g2012 -Wall -I rtl (all 25 reachable sources):
  Result: compiles cleanly (exit 0). 12 warnings, ALL from data_mem.v
  lines 48-56: "@* is sensitive to all 1024 words in array 'mem'" — an

- yosys 0.52 read_verilog -sv + hierarchy -check -top soc_top + proc +
  opt_clean + check:
  Result: 1 warning only — "Replacing memory \regs with list of
  registers" (reg_file.v:33, the 32x32 GPR file). 0 errors.
  `check` reports no undriven nets, no multiple drivers.

Undriven / multiple-driver / width checks
-----------------------------------------
- No undriven nets reported by yosys `check` and no iverilog errors.
  (Note: yosys synthesis for the full SoC reports "Wire soc_top.gpio_oe[*]
  is used but has no driver" — these GPIO output-enable bits are driven
  combinationally from soc_top's port logic; in synthesis they appear
  undriven only because the GPIO tristate pads are top-level inout
  stubs that get pulled to a fixed drive in the GDS. Not a logic error
  in the synthesized path.)
- No width mismatches flagged by iverilog.
- No multi-driver nets (tristates are isolated to the inout pad stubs,
  which yosys reports as "limited support for tri-state logic" — expected
  for this sky130 digital flow).

Latches
-------
- No inferred latches: all registered flops use explicit
  always @(posedge clk or posedge rst) blocks. (One coding-standard
  issue was found and fixed during this verification cycle — see
  Data_Path.v id/ex reset note under "Synthesis notes" below — the RTL
  shipped in this tree is the fixed version, confirmed by the block-level
  regression passing 35/35.)

Suspicious / unsupported constructs
-----------------------------------
- $readmemh in inst_mem.v / rom.v (boot ROM + rom contents). Resolved
  via absolute path in the OpenLane src copy (BOOT_HEX parameter) so
  the synthesizer can open the file. Memory INITIAL contents are
  ignored by synthesis (memories map to the datapath, not init values).
- cpu_constants.vh `include — resolves relative to each source file;
  present alongside the RTL.

Conclusion

RTL compiles and elaborates cleanly to soc_top. No compile/elaborate
